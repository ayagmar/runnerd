## The service

`runnerd init` writes a user unit that runs `runnerd serve`:

```ini
[Unit]
Description=runnerd: ephemeral GitHub Actions runners
Documentation=https://ayagmar.github.io/runnerd/

[Service]
Type=exec
ExecStart="/home/dana/.local/bin/runnerd" serve --config "/home/dana/.config/runnerd/runnerd.toml"
Restart=on-failure
RestartSec=10

[Install]
WantedBy=default.target
```

```sh
systemctl --user enable --now runnerd   # start now and at login
loginctl enable-linger "$USER"          # keep it running while you are logged out
journalctl --user -u runnerd -f         # its log
systemctl --user restart runnerd        # after editing runnerd.toml by hand
systemctl --user stop runnerd           # exits within 45s; running jobs carry on
```

`systemctl stop`, SIGTERM and SIGINT remove idle and warm runners and exit within 45 seconds, even if Docker or GitHub do not answer. Runners of running jobs and the registry mirror stay up for the next start to adopt; meanwhile those jobs restore and save nothing in the caches runnerd serves. A second signal kills running jobs.

`runnerd stop` waits for running jobs, then removes every runner and the mirror, so nothing is left behind. `runnerd stop --force` kills running jobs instead.

## How it schedules

- It reads the `gh` CLI's token at start, and again when GitHub rejects it. Every [`poll_interval`](../configuration/#host) it asks GitHub for each repository's queued jobs.
- The pool whose `labels` include every label in a job's `runs-on` serves it: one `[[repositories]]` entry, or one of [several](../configuration/#split-light-and-heavy-jobs).
- It registers a just-in-time runner and starts it in a free slot of the pool's profile if the slice's `MemoryMax` has room for the profile's `memory` (under [measured admission](../admission/#measured-admission), the job's predicted peak) and, under [CPU admission](../admission/#cpu-admission), the CPU budget has room too.
- A runner takes one job, then runnerd removes it. A runner with no job after 5 minutes is removed unless it is [warm](#warm-runners).
- Each tick removes the idle runners it no longer needs first, all at once, then starts runners for queued jobs. A runner that no longer fits what runs by then waits; the others start, then the tick plans again from the same listings (at most three times) instead of waiting for the next poll.
- A job's page shows when runnerd first saw it queued (*Seen by runnerd*; a job a waiting runner took before any listing showed it has none, nor do jobs recorded by older versions), so its wait splits into the time before runnerd knew of it, the time it took to start a runner, and the runner's boot.
- A restarted runnerd adopts running runner containers.

## Warm runners

A job that finds no runner waits 15 to 25 seconds for the next poll, a registration and a container start. A warm runner is registered before GitHub queues the job and takes it within a second or two.

- Each pool keeps [`warm`](../configuration/#repositories) runners (1 by default) while its repository is active: a job was queued in the last hour, or it is an hour of the day (UTC) its jobs came in on 3 of the last 14 days. Otherwise they go after 5 idle minutes.
- When a job is seen, the other jobs of its run get runners too: per pool, the median number that workflow's runs had there over 14 days (from 3 runs), less those seen.
- Warm runners start last, once every queued job that fits has a runner, and reserve their profile's `memory` (and `cpus` under CPU admission). A queued job of another repository takes their room. After a job in slot 1, the profile measures what slot 1 changed without stopping anything, at most every 10 minutes. Only a reseed due by that measure (slot 1 reached [`reseed_at`](../configuration/#caches)) or asked for removes them, once its other runners are idle.

## Warm caches

A slot is one concurrent job of a profile: each job gets a new container, and the slot keeps a volume over the profile's read-only snapshot. A queued job starts in the free slot that last ran the same job (repository, workflow, job name), else one that ran a job of its repository, else the lowest free slot.

<Caches />

| Cache | Kept |
|---|---|
| the slot's Docker images, `~/.cache`, tool cache, Android SDK | per slot, between jobs, for every repository and branch |
| the slot's Docker build cache | per slot. Build contexts go first, then layers, least recently used first, to about half the slot's share; cache mounts (`RUN --mount=type=cache`) stay up to three quarters. Slots together get a quarter of the free disk plus what their volumes hold, 1 GB to 20 GB each |
| cargo credentials, Gradle's `gradle.properties` and init scripts, Maven's `settings*.xml`, Hugging Face tokens | never kept. Anything else a job leaves, jobs of other repositories see ([trust boundary](../configuration/#caches-are-shared-between-repositories)) |
| the profile's snapshot | replaced by slot 1's changes once they reach [`reseed_at`](../configuration/#caches) and the profile is idle, which drops every slot's own changes. One that would pass `snapshot_max` starts over from the image instead |
| pnpm store, Maven repository, Docker Hub mirror | shared by all slots; emptied above their [`max_size`](../configuration/#caches) when no runner runs |
| [build cache](#build-cache) | per repository; least recently used entries go above [`build.max_size`](../configuration/#caches) |

`docker/setup-buildx-action` starts a new BuildKit container per job, which keeps none of this; set `driver: docker` to build on the slot's Docker Engine, as `docker build` does.

## Build cache

One store per repository, kept in `~/.cache/runnerd/build-cache`, that every runner reaches: a task built in slot 2 is a hit in slot 3, and a pull request's build gets what `main` built.

| Tool | Uses the cache when |
|---|---|
| Gradle | the build enables caching (`org.gradle.caching=true` or `--build-cache`) and sets no remote cache |
| sccache | the workflow runs it (`RUSTC_WRAPPER=sccache`) with no other backend |
| Bazel | `.bazelrc` sets no `--remote_cache` |
| Turborepo | always; a `TURBO_API`, `TURBO_TOKEN` or `TURBO_TEAM` the workflow sets wins |
| Nx | the workflow opts in (below) and uses no Nx Cloud |

Nx fails the run when its cache does not answer, so a step before Nx opts in:

```yaml
- run: '[ -z "$RUNNERD_BUILD_CACHE_URL" ] || echo "NX_SELF_HOSTED_REMOTE_CACHE_SERVER=$RUNNERD_BUILD_CACHE_URL/nx" >> "$GITHUB_ENV"'
```

A job writes only when GitHub says it runs a push, schedule or manual run (`workflow_dispatch`) of the default branch or of one of [`build.branches`](../configuration/#caches). With `build_cache_writers = "pull-requests"` ([Configuration](../configuration/#repositories)), a `pull_request` event from the repository's own branch that a person, not a bot, opened, reopened or pushed to also writes. Anyone who can push a branch can then change what `main` builds load, so enable it only where that is you. runnerd asks GitHub about each job's runner, trigger and commit; nothing a job writes to its log or environment counts. Every other job, fork and bot pull requests included, reads only; its uploads are answered as stored and dropped.

sccache uses the shared cache instead of its disk cache in the slot, not as well as it: a pull request's own compilations are not kept, so a second push compiles again what the first did. A Rust repository with many pull requests may do better with its own backend or `build_cache = false`.

Containers a job starts itself, such as `container:` jobs, do not reach the cache. `build_cache = false` under a repository keeps it out; a workflow turns off Gradle's part with `RUNNERD_BUILD_CACHE_URL: ""` and Turborepo's with `TURBO_CACHE: local:rw`. `runnerctl caches --clean runnerd-build-cache` empties it.

### GitHub Actions' cache

The build cache also serves `actions/cache`, the `cache:` input of `setup-node`, `setup-java`, `setup-python` and `setup-gradle`, and Docker's `type=gha` cache, with no workflow change, in place of GitHub's. Entries count within `build.max_size`. `build.actions_cache = false` under [`[caches]`](../configuration/#caches), or a repository's `build_cache = false`, leaves jobs on GitHub's cache; `runnerd doctor` and `runnerctl caches` say which.

Entries are scoped as on GitHub, and only [the jobs that may write](#build-cache) save. A default-branch or `build.branches` job saves into its branch and restores from it, then the default branch. An opted-in pull request saves into its own scope and restores from it, then its base branch, then the default branch. Every other job restores from the default branch, and its saves report success and are dropped. Artifacts (`upload-artifact`, `download-artifact`) still go to GitHub through runnerd and fail while it restarts; the actions retry for about 25 seconds. `container:` jobs, `docker://` actions and containers a job starts use GitHub's cache.

## Records of failed jobs

With `record_failures` on a profile ([Configuration](../configuration/#records-of-failed-jobs)), a failed job's stopped runner is committed to an image, `runnerd-record:<job>`, before it is removed. `runnerctl shell <job>` starts a container from it and opens bash in the job's workspace, after printing the step that failed and what it ran:

```console wrap=false
$ runnerctl shell 120055991489
runnerd: the record of job 120055991489 of halyard/ledger, CI / build
It failed at step 5: Unit tests (exit code 1)
Its log shows it ran:
    ./gradlew test --no-daemon
    shell: /usr/bin/bash -e {0}
You are in /home/runner/_work/ledger/ledger, as the job left it. Not kept: the job's Docker containers and images; what it changed in ~/.cache, the tool cache and the Android SDK, which show the profile's snapshot; and what it added or changed among your home's dot-files and in /tmp (logins, and tools in ~/.local or ~/.nvm), except ~/.rustup and ~/.cargo's bin, registry and git. Exit to remove this container.
runner@4be1c0d2a7e9:~/_work/ledger/ledger$
```

`--step 3` shows step 3 instead. The shell's container counts against the budget with the profile's memory cap and is refused when it does not fit. It mounts the caches read-only, blocks the profile's reseed while open, and ends with the shell, the client or after 8 hours.

A record keeps the workspace with build output and test reports, the runner's `_diag` logs (secrets masked), and what the job wrote outside volumes. It never keeps logins and tools in the runner's home (`.gitconfig`, `.aws`, `~/.local`, `~/.nvm`), `/tmp`, the JIT config, `_work/_temp` or the token `actions/checkout` puts in `.git/config`; runnerd refuses to keep a container that still holds any. runnerd does not read file contents, so a secret saved in the workspace stays.

Anyone who can use Docker on this host can read a record (`docker run runnerd-record:<job>`), so turn `record_failures` on only for profiles whose jobs they may see. A record takes about twice what the job wrote outside volumes. `runnerctl records` lists them; `runnerctl records rm <job>`, `--all` or `--older-than 2d` removes them.

## Job history

runnerd records every job its runners may run in SQLite; [`[history]`](../configuration/#history) sets its path and retention. For each job:

| What | Kept |
|---|---|
| its timeline (queued, container started, job started, finished) and steps, as GitHub shows them | with the job |
| the container's CPU, memory and network every 2 s, its CPU throttling and the bytes the Docker Hub mirror served it | samples for `history.samples`; totals and peaks with the job |
| its log, secrets still masked, up to `history.log_max` | for `history.logs` |

A job's wait runs from queued to started; the part that passed while runnerd was not running is kept as `unseen` and left out of the waits [sizing](../admission/#how-a-wait-is-counted) reads.

A job that leaves GitHub's queue without one of this machine's runners is recorded as `elsewhere` (the dashboard's "Not run here"), as `cancelled in queue` when its run was cancelled first, or as its conclusion, such as `skipped`. No wait, median or cost counts it. A finished job goes after `history.jobs`.

## API

JSON over `$XDG_RUNTIME_DIR/runnerd.sock` (`curl --unix-socket`), mode 0600: only the user runnerd runs as may connect. Types: [`crates/core/src/api.rs`](https://github.com/ayagmar/runnerd/blob/main/crates/core/src/api.rs). Times are Unix seconds, sizes bytes, CPU millicores.

| Request | Response |
|---|---|
| `GET /v1/status` | profiles, slots, runners, repositories with their queued jobs, the budgets |
| `POST /v1/repositories/{owner}/{name}/pause?force=`, `.../resume` | `409` naming the running job, unless `force=true` cancels its run; `204`. Without `{owner}/{name}`, for every repository |
| `POST /v1/profiles/{name}/reseed` | `202`; `409` while it reseeds or a record shell is open in it |
| `POST /v1/caches/{name}/clean` | `204`; `409` naming the jobs that use the cache |
| `GET /v1/config`, `POST /v1/config/check`, `GET /v1/doctor` | the file's text and revision, secrets as `"<secret>"`; `check-config` on a TOML body; `runnerd doctor`'s checks |
| `PUT /v1/config?revision=` with TOML | checks, writes and applies it; `422` invalid, `500` not writable, `503` stopping, all leaving everything as it was. A `revision` older than the file (an edit, or [auto sizing](../admission/#auto-sizing)) answers `409` |
| `POST /v1/shutdown` with `{"force": false}` | `202`; `true` kills running jobs |
| `GET /v1/jobs?repository=&state=&conclusion=&workflow=&name=&since=&until=&before=&limit=` | jobs, newest first; `next` is the next page's `before` |
| `GET /v1/jobs/{id}`, `.../samples`, `.../logs?from=&follow=` | a job with timeline, steps and metrics; its samples; its log, open until the job is final with `follow=true` |
| `POST /v1/notify/test?target=` | a test message to every `[notify]` target or the one named; `404` without targets |
| `GET /v1/records`, `DELETE /v1/records/{job}`, `DELETE /v1/records?all=true`, `?older_than=2d` | the records; the ones removed (a record with a shell open stays; by job it answers `409`) |
| `POST /v1/records/{job}/shell?step=&cols=&rows=` with `Connection: Upgrade`, `Upgrade: runnerd-tty` | `101`, then raw terminal bytes both ways; `409` when the budget is full |
| `GET /v1/dashboard`, `POST /v1/dashboard/sign-out`, `POST /v1/dashboard/pairings?origin=` | `[web] open`; signs every browser out; a 5-minute login link for one of `[web] origins` |
| `GET /v1/events?job=&logs=` | server-sent events, below |

Read-only: `GET /v1/host/samples`, `/v1/stats`, `/v1/activity`, `/v1/sizing` ([advice](../admission/#sizing)), `/v1/insights?days=` ([Insights](../insights/); 14 days by default, 90 at most), `/v1/digest`, `/v1/savings`, `/v1/caches` and `/v1/caches/history`.

A forced pause cancels the runs of the repository's running jobs, other jobs of those runs included, and removes a runner still running 90 s later. A paused repository's waiting runners, warm ones too, stop at once. A pause lasts until a resume, across restarts.

### Events

`job.queued`, `job.started`, `job.step` and `job.finished` follow a job. `slot.changed`, `budget.changed`, `profile.changed`, `profile.removed`, `repository.changed` and `repository.removed` carry the state after a change, not each transition. `cache.reseeded` marks a new snapshot, `record.created` and `record.deleted` a record's fate, `sizing.changed` an [auto sizing](../admission/#auto-sizing) write, and `runner.failed` a runner that could not be registered or started (once, until one of the repository's runners takes a job). `job.sample`, `host.sample` and `log.line` (`logs=true`) are live.

Every other event has an ID. Send the last one seen as `Last-Event-ID` and the stream resumes after it, across daemon restarts.

### Reloading

A config saved through the dashboard or `PUT /v1/config` applies without a restart, and running jobs keep running; after a hand edit, restart the service. A removed profile, or slots past a lowered `slots`, stay until their runners finish. A waiting runner, warm ones included, is removed when its repository is removed or moved, or its `labels` or the profile's `image`, `memory` or `cpus` changed, by hand or by auto sizing; a new `image` waits until Docker has it. `[web]`, `history.database` and `caches.build.directory` change only at the next start.
