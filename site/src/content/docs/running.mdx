## The service

`runnerd init` writes a user unit that runs `runnerd serve`:

```ini
[Service]
Type=exec
ExecStart="/home/dana/.local/bin/runnerd" serve --config "/home/dana/.config/runnerd/runnerd.toml"
Restart=on-failure
RestartSec=10

[Install]
WantedBy=default.target
```

```sh
systemctl --user enable --now runnerd   # start now and at login
loginctl enable-linger "$USER"          # keep it running while you are logged out
journalctl --user -u runnerd -f         # its log
systemctl --user restart runnerd        # after editing runnerd.toml by hand
systemctl --user stop runnerd           # waits for running jobs, up to systemd's stop timeout
```

A config saved from the dashboard or `PUT /v1/config` applies without a restart, except `[web]` and `history.database`. `runnerd stop` waits for running jobs too; `runnerd stop --force`, or a second signal, kills them.

Runner containers live in Docker, not in the unit: a restarted runnerd adopts the ones still running, and keeps the repositories it had paused paused.

## How it schedules

- It reads the `gh` CLI's token at start, and again when GitHub rejects it.
- Every `poll_interval` (`[host]`, default `15s`) it asks GitHub for each repository's queued jobs.
- A job is served when every label in its `runs-on` is in its repository's `labels`.
- For each one it registers a just-in-time runner and starts it in a free slot of the repository's profile, if the slice's `MemoryMax` still has room for the profile's `memory`, or with [measured admission](../configuration/#measured-admission) for the job's predicted peak, and under [CPU admission](../configuration/#cpu-admission) if the CPU budget has room for it too. Other jobs wait in GitHub's queue.
- The runner takes one job, its container exits, and runnerd removes it. A runner with no job after 5 minutes is removed.
- A restarted runnerd adopts the runner containers still running and deletes this host's runners that have none.
- Before a profile's first runner it pulls the profile's `image`, logging the pull's progress.

## Warm caches

A slot is one concurrent job of a profile. Each job gets a new container, but the slot keeps a volume over the profile's read-only snapshot. The images point every common toolchain's cache into `~/.cache`: rustup and cargo, Go modules and builds, Gradle, Maven, npm, Yarn, Bun, pip, uv, Poetry, pub, Deno and coursier.

<Caches />

| Cache | Kept |
|---|---|
| the slot's Docker images, `~/.cache`, tool cache, Android SDK | per slot, between jobs |
| cargo's credentials and config, Gradle's `gradle.properties` in `~/.cache` | never: no later job or record shell sees them, even from an older snapshot |
| the profile's snapshot | replaced by slot 1's changes once they reach `reseed_at` (`[caches]`, default `2G`) and the profile is idle; above `snapshot_max` (default `10G`) it starts over from slot 1's changes alone |
| pnpm store, Maven repository | shared by all slots, emptied above `max_size` when no job runs |
| Docker Hub mirror | runs while any runner does; its storage is emptied above `mirror.max_size` (default `10G`) when no job runs |

## Records of failed jobs

With `record_failures` on a profile ([Configuration](../configuration/#records-of-failed-jobs)), a failed job's stopped runner is committed to an image, `runnerd-record:<job>`, before it is removed. `runnerctl shell <job>` starts a container from it and opens bash in the job's workspace, after printing the step that failed and what it ran:

```console wrap=false
$ runnerctl shell 120055991489
runnerd: the record of job 120055991489 of halyard/ledger, CI / build
It failed at step 5: Unit tests (exit code 1)
Its log shows it ran:
    ./gradlew test --no-daemon
    shell: /usr/bin/bash -e {0}
You are in /home/runner/_work/ledger/ledger, as the job left it. Not kept: the job's Docker containers and images; what it changed in ~/.cache, the tool cache and the Android SDK, which show the profile's snapshot; and what it added or changed among your home's dot-files and in /tmp (logins, and tools in ~/.local or ~/.nvm), except ~/.rustup and ~/.cargo's bin, registry and git. Exit to remove this container.
runner@4be1c0d2a7e9:~/_work/ledger/ledger$
```

`--step 3` shows step 3 instead.

- The terminal goes over the API socket and keeps the size it was opened with.
- The shell's container counts against the budget with the profile's memory cap, and is refused when the budget cannot hold it, or under [measured admission](../configuration/#measured-admission) while the slice is at 90% of `MemoryMax`.
- It mounts the profile's snapshot and the shared pnpm and Maven caches read-only. While it is open, the profile does not reseed (`runnerctl reseed` answers 409) and the shared caches are not trimmed or cleaned. It is refused while the profile reseeds or the shared caches are trimmed.
- It goes when the shell exits, when the client goes away, or after 8 hours.

| What | In a record |
|---|---|
| the workspace, `_work/<repository>`, with build output and test reports | yes |
| the runner's `_diag` logs, secrets masked as the runner masks them on GitHub | yes |
| a Rust toolchain in `~/.rustup` and `~/.cargo`'s `bin`, `registry` and `git`, for a job that sets `RUSTUP_HOME` and `CARGO_HOME` there (the images put both in `~/.cache`) | yes |
| anything else the job wrote outside volumes and the places below, such as a tool unpacked in `/opt` | yes |
| other dot-files and dot-directories the job added or changed in the runner's home: logins (`.gitconfig`, `.aws`, `.gnupg`, `.docker`, `~/.cargo/credentials.toml` and `config.toml`, the runner's `.credentials`) and tools installed there (`~/.local`, `~/.nvm`, `~/.dotnet`, `~/.bun`, `~/.sdkman`); what it added or changed in `/tmp` and `/var/tmp` | never |
| the JIT config, `_work/_temp` (step scripts), the token `actions/checkout` puts in `.git/config` | never |
| the slot's caches (rustup and cargo included), tool cache, Android SDK, and the job's Docker images | no; volumes, which a shell sees as the profile's snapshot |

The runner image deletes the "never" rows when the runner exits, and runnerd refuses to keep a container whose changes still hold any of them. A step that saves a secret into the workspace or elsewhere outside those places leaves it in the record: runnerd does not read file contents.

Records are readable by anyone who can use Docker on this host (`docker run runnerd-record:<job>`), and by the user runnerd runs as, through its socket, which is the only client the socket accepts. Turn `record_failures` on only for profiles whose jobs you would let those users see.

Records take disk: committing one takes a second or two, and it takes about twice what the job wrote outside volumes, since Docker keeps the layer packed and unpacked. `runnerctl records` lists them with their limits; `runnerctl records rm <job>`, `--all` or `--older-than 2d` removes them. The job history keeps, after a record is gone, when it was made, its size, and why it went (`count`, `size`, `age` or `user`).

## Job history

runnerd records every job its runners may run in a SQLite database, `$XDG_STATE_HOME/runnerd/runnerd.db` by default. `[history]` in the config changes the path and how long each part is kept. For each job:

| What | Kept |
|---|---|
| its timeline: queued, container started, job started, finished, container and runner registration removed | with the job |
| its steps with their start and end, as GitHub shows them | with the job |
| CPU, memory and network of its container, sampled every 2 s | samples 7 days (`history.samples`); totals and peaks with the job |
| the bytes the Docker Hub mirror served it | with the job |
| its log, as GitHub shows it with masked secrets still masked, up to 50M (`history.log_max`) | 30 days (`history.logs`) |

A finished job's record goes after 90 days (`history.jobs`), with its steps and runner. The database file does not shrink when rows go; SQLite reuses the space. runnerd also keeps the sizes of the cache volumes and the slice's CPU and memory over time.

Where the data comes from:

- **Which job a runner took**: a small script runnerd runs in the container (`docker exec`, as root) reads the job's ID from the runner's `_diag/Worker_*.log` within a second of the job starting. GitHub's list of queued jobs still shows the job for several seconds after that, and runnerd does not start a second runner for it.
- **Steps**: GitHub's jobs API, read every poll while a job runs. The runner's own logs name steps differently from GitHub (`Set up runner` for `Set up job`) and change between runner versions. The API's times have second precision.
- **The log**: the runner's `_diag/pages`, which the same script follows. The runner writes the log there in 4 KiB blocks, so lines arrive a block at a time, and a quiet step's lines arrive when it ends.
- **CPU and memory**: the container's cgroup files. A container's memory is an estimate of what its job holds without page cache: `memory.current` less the file page cache lists, so lower than `docker stats`, which still counts page cache read twice. The slice's memory is `memory.current` less inactive page cache, as `docker stats` counts it, so the high-water mark errs toward holding starts back. Kills and out-of-memory events come from `memory.events`. Network from `/proc/<pid>/net/dev`.

## API

JSON on `$XDG_RUNTIME_DIR/runnerd.sock`, mode 0600: only the user runnerd runs as may connect. The types are in [`crates/core/src/api.rs`](https://github.com/ayagmar/runnerd/blob/main/crates/core/src/api.rs) and its modules. Times are seconds since the Unix epoch, sizes bytes, CPU millicores.

| Request | Response |
|---|---|
| `GET /v1/status` | profiles and their slots, running runners, repositories with their queued jobs, the memory budget with the mirror's and each seed container's share, and under `cpu_overcommit` the CPU budget |
| `POST /v1/repositories/{owner}/{name}/pause?force=` | no new runners; `409` naming the running job, unless `force=true` cancels its run |
| `POST /v1/repositories/{owner}/{name}/resume` | `204` |
| `POST /v1/repositories/pause?force=`, `POST /v1/repositories/resume` | the same for every configured repository; while any runs a job, `409` naming the jobs, and none is paused |
| `POST /v1/profiles/{name}/reseed` | `202`; the profile starts no runner until its slots are free and slot 1 became its snapshot; `409` while it reseeds or a shell is open in one of its records |
| `POST /v1/caches/{name}/clean` | `204`; removes a slot's volume or a shared cache; `409` naming the jobs that use it |
| `GET /v1/config` | the config file's path, text and revision |
| `POST /v1/config/check` with TOML | what `runnerd check-config` says about it |
| `PUT /v1/config?revision=` with TOML | checks it, writes it in place of the file and runs with it; invalid (`422`), not writable (`500`) or runnerd stopping (`503`) leaves the file and what runs as they were. With `revision`, from `GET /v1/config`, a config replaced since, as by [auto sizing](../configuration/#auto-sizing), or a file edited on disk since, is not overwritten (`409`); the reply's `revision` is that of the text written, to send with the next change |
| `GET /v1/doctor` | `runnerd doctor`'s checks, for the config runnerd runs with |
| `POST /v1/shutdown` with `{"force": false}` | `202` |
| `GET /v1/jobs?repository=&state=&conclusion=&since=&until=&before=&limit=` | a page of jobs, newest first; `next` is the `before` of the next page |
| `GET /v1/jobs/{id}` | a job with its timeline, steps, metrics and log size |
| `GET /v1/jobs/{id}/samples` | its CPU, memory and network over time |
| `GET /v1/jobs/{id}/logs?from=&follow=` | its log as text; with `follow=true`, open until the job's record is final |
| `GET /v1/host/samples?since=` | the slice's CPU and memory, the last 24 hours at most |
| `GET /v1/stats?repository=&since=&until=&bucket=day` | finished jobs per repository and day (or `hour`), 744 buckets back at most: counts, queue and run time, CPU, memory, mirror bytes |
| `GET /v1/sizing?since=` | per configured profile and per job (repository, workflow, name): percentiles of the sampled memory and CPU peaks, waits, how busy the slots were, and the [advice](../configuration/#sizing) for `memory` and `slots`; whether [auto sizing](../configuration/#auto-sizing) is on and the changes it made; the last 30 days by default |
| `GET /v1/caches`, `GET /v1/caches/history?since=` | cache volume sizes and their limits, now and over time |
| `GET /v1/records` | every record of a failed job, oldest first, with the limits and the jobs whose record has a shell open |
| `DELETE /v1/records/{job}`, `DELETE /v1/records?all=true`, `DELETE /v1/records?older_than=2d` | the jobs whose records went and the disk they took; records with a shell open stay, and removing one by its job is refused with `409` |
| `POST /v1/records/{job}/shell?step=&cols=&rows=` with `Connection: Upgrade`, `Upgrade: runnerd-tty` | `101`, then the connection is the shell's terminal, raw bytes both ways; `409` when the budget is full |
| `GET /v1/events?job=&logs=` | server-sent events, below |

```sh
curl --unix-socket "$XDG_RUNTIME_DIR/runnerd.sock" http://runnerd/v1/status
curl --unix-socket "$XDG_RUNTIME_DIR/runnerd.sock" -X POST http://runnerd/v1/repositories/halyard/ledger/pause
curl -N --unix-socket "$XDG_RUNTIME_DIR/runnerd.sock" http://runnerd/v1/events
```

### Events

| Event | Sent when |
|---|---|
| `job.queued`, `job.started`, `job.step`, `job.finished` | a job moves on |
| `slot.changed` | a runner comes or goes in a slot |
| `profile.changed` | a reload adds or changes a profile, or it starts or stops reseeding |
| `profile.removed` | a reload removed it and its last runner is gone |
| `repository.changed` | paused or resumed, its queue changed, or a reload added or changed it |
| `repository.removed` | a reload removed it |
| `budget.changed`, `cache.reseeded` | the budget changed; a profile has a new snapshot |
| `record.created`, `record.deleted` | a failed job's runner was kept as a record; a record went, and why |
| `sizing.changed` | [auto sizing](../configuration/#auto-sizing) wrote a profile's new `memory` and `slots`; it carries the old ones |
| `job.sample`, `host.sample`, `log.line` | live: a sample, or a log line with `logs=true` |

Every event but the live ones has an ID: send the last one seen as `Last-Event-ID` and the stream resumes after it, across daemon restarts. Live events are not stored; a client that missed some reads the job's samples or log.

`slot.changed`, `profile.changed`, `budget.changed` and `repository.changed` carry the state after a change, not each transition: a pause and a resume that land before the daemon publishes its status send nothing. Applying `profile.*` and `slot.changed` to a status's profiles, and `repository.*` to its repositories, keeps them equal to what `/v1/status` returns.

### Pausing

A forced pause cancels the run of each of the repository's running jobs. GitHub cancels runs, not single jobs, so the run's other jobs are cancelled too. The runner reports the job cancelled, which takes under a minute; one still running 90 s later is removed, and its registration is deleted once GitHub lets go of it.

A pause lasts until a resume, across restarts: the job history records the paused repositories, and a restarted daemon starts no runner for them. If the history cannot record a pause or resume, the change holds until the daemon restarts, and the request fails with `500` saying so. A reload that removes a paused repository forgets its pause; added back, it starts active.

### Reloading

A new config takes effect without a restart, and running jobs keep running. A removed profile, or slots past a lowered `slots`, stay until their runners finish, and no runner starts in a profile while it runs as many as its `slots`. A runner still waiting for a job of a removed repository, or of one moved to another profile, is removed. Runners started afterwards get the new limits, image and labels. `history.database` changes only at the next start.
