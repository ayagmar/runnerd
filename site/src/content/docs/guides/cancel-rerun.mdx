On a job's page in the dashboard, **Cancel run**, **Re-run job** and **Re-run failed jobs**; in the TUI's job view, `x`, `a` and `A`; from a shell, `runnerctl cancel` and `runnerctl rerun`. Each shows what GitHub would do and sends nothing until you confirm it.

GitHub cancels runs, not jobs, and a re-run takes the jobs that depend on the one re-run with it. So `runnerctl cancel` and `runnerctl rerun` first read the run from GitHub, print what GitHub would do to its current attempt and the other jobs of the run runnerd knows (GitHub may have more, on other runners), and send nothing. They end with a command such as `runnerctl cancel 9001 --confirm 3f9a…`, which sends what they showed, once, within 5 minutes. If the run has moved to another attempt by then, or runnerd's config changed, nothing is sent: you get a new preview. If GitHub would not show the run, there is nothing to confirm until it does. `--force` skips the preview and sends at once, for scripts. The answer is one of four: GitHub took it, the run had already finished, GitHub refused (with its HTTP status and what to check), or the outcome is unknown, as after a timeout; then check the run on GitHub before asking again. runnerd's own record of the job stays as it was; the cancelled job and the new attempt arrive as GitHub lists them. [`[github] job_actions = false`](../../reference/configuration-more/#github) turns both off.

## Runner faults

With `rerun_runner_faults = true` on a [repository](../../reference/configuration/#repositories), runnerd re-runs a run its runner failed without asking. It is off by default because a runner fault is read from what the failed step printed, and a job's own code can print the same words, as a test of mount errors would.

When a job ends as a [runner fault](../../concepts/terms/#job-history), the run completed as a failure and every other job of its attempt that failed or was cancelled is a runner fault too, runnerd asks GitHub to re-run the run's failed jobs, without a preview. It does it from a run's first and second attempts only, and never once the run is at a later attempt. GitHub's re-run names no attempt, so if a person re-runs the run in the second before runnerd's request goes out, the run gets one more attempt. A job that failed in its code, on another machine, or a run cancelled as a whole leaves the run alone. When GitHub does not say whether it took the request, as after a timeout, runnerd does not ask again. The job's page then says *runnerd re-ran the run's failed jobs as attempt 2*. If GitHub refuses, as for a token without Actions: write, runnerd holds that repository's re-runs for an hour and says so in the attention list. `job_actions = false` turns it off too.

A classic token needs the `repo` scope, a fine-grained one Actions: write; `runnerd doctor` says what it can tell without trying. [Security model](../../security/#job-actions) says what these actions can do on GitHub.
